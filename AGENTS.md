# Repository Guidelines

## Project Overview

- GlossaryGo is a Raycast extension written in strict TypeScript.
- `package.json` is both the package manifest and the Raycast extension manifest. Keep its command declarations synchronized with their entry points in `src/`.
- The current command ID is `searh-term`, which maps to `src/searh-term.ts`. The spelling is part of that mapping; if it is corrected, rename the manifest entry and source file together.
- The extension currently targets both macOS and Windows. Do not add platform-specific APIs or shell assumptions without a guard and an intentional manifest change.
- This repository is still a minimal scaffold. Do not infer product behavior that is not documented in the issue, request, README, or existing code.

## Repository Layout

- `src/`: Raycast command entry points and supporting TypeScript modules.
- `assets/`: bundled extension assets. `package.json` references `assets/extension-icon.png` as `extension-icon.png`.
- `package.json`: extension metadata, command registry, dependencies, and scripts.
- `tsconfig.json`: strict TypeScript configuration targeting ES2023.
- `eslint.config.js` and `.prettierrc`: Raycast lint rules and formatting settings.
- `README.md` and `CHANGELOG.md`: user-facing documentation and release notes.
- `raycast-env.d.ts`: generated by Raycast tooling and ignored by Git; do not edit it manually.

## Package Manager and Commands

This repository is an explicit exception to the global Bun preference. Use npm exclusively. Do not run `bun`, `bunx`, `pnpm`, or `yarn`.

```bash
npm install
npm run dev
npm run lint
npm run fix-lint
npm run build
```

- Use `npm install <package>` or `npm install --save-dev <package>` for dependency changes and `npx` for one-off executables.
- Keep `package-lock.json` synchronized with `package.json`; do not introduce a Bun lockfile.
- `npm run dev` starts Raycast development mode with automatic reload.
- `npm run lint` validates the manifest and runs ESLint and Prettier checks.
- `npm run fix-lint` applies automatic lint and formatting fixes; inspect its diff afterward.
- `npm run build` performs the production bundle and TypeScript validation.
- No automated test command is configured yet. Do not claim tests passed. If tests are introduced, add a package script and run it with `npm run`.
- Publishing is an external action and requires an explicit user request. When authorized, use the existing `npm run publish` workflow.

## Raycast Conventions

- A manifest command named `<command>` must have a matching `src/<command>.ts`, `.tsx`, `.js`, or `.jsx` entry point.
- Preserve the declared command mode. The current `no-view` command should perform its work in a default exported function and use Raycast feedback APIs for success and failure states.
- Prefer `@raycast/api` components and APIs and `@raycast/utils` helpers over custom substitutes when they cover the use case.
- Keep manifest titles, descriptions, platforms, categories, preferences, and assets aligned with actual behavior. Raycast lint treats manifest validation as part of linting.
- Use Raycast Preferences for user configuration and secrets. Never commit credentials, tokens, or user-specific data.
- Keep user-facing messages concise and actionable. Handle expected failures explicitly and do not expose raw upstream errors.

## TypeScript and Formatting

- Keep TypeScript strict; avoid `any`. Use `unknown` at untrusted boundaries and narrow it before use.
- Follow the repository Prettier settings: double quotes and a 120-character print width.
- Use `camelCase` for values and functions and `PascalCase` for React components and exported types.
- Prefer small, focused modules and `async`/`await` for asynchronous flows.
- Use `.ts` for non-UI commands and helpers; use `.tsx` only when the file renders React/Raycast UI.
- Treat user input and external responses as untrusted. Validate data before using, persisting, or rendering it.

## Verification and Documentation

- For source, dependency, or manifest changes, run `npm run lint` and `npm run build` before handing off. Report exact failures instead of hiding or broadening the change to fix unrelated issues.
- For interactive behavior, also run `npm run dev` and manually exercise the affected command in Raycast when the environment allows it; report when manual verification was not possible.
- Update `README.md` when setup, preferences, or user-visible workflows change.
- Update `CHANGELOG.md` for user-visible changes. Preserve Raycast's `{PR_MERGE_DATE}` placeholder in new release sections.
- Never publish, push, or open a pull request unless the user explicitly requests it.
