# Term Actions Design and Implementation Plan

> **For agentic workers:** Use superpowers:executing-plans to implement this plan task by task. Steps use checkboxes for tracking. Delegate each local commit to a separate `gpt-5.6-luna` agent with low reasoning, as required by this repository.

**Goal:** Add **Add Term**, **Edit Term**, and **Delete Term** to the existing **Search Term** window's action menu.

**Architecture:** Keep Search Term as the single Raycast command. Its selected-result action menu opens Add Term or Edit Term forms and offers Delete Term for that selection. Pure YAML transformations and a shared file-writing service reuse the existing validation pipeline. The current command-level Glossary File preference supplies the target path.

**Tech Stack:** TypeScript, React, Raycast API, the installed `yaml` package, Node filesystem APIs, and Vitest. No new runtime dependency is planned.

**Spec:** The behavior and decisions below form the design for this plan. This is a planning artifact, not an instruction to begin implementation.

## Behavior and decisions

**Latest scope correction:** the user confirmed **Add Term**, **Edit Term**, and **Delete Term** as actions in the existing Search Term window's menu, not separate Raycast commands. This correction replaces the earlier standalone-command design and removes the need for preference migration.

**Retained decisions:** direct saving with search-query prefill, duplicate rejection, trimming new term names, rejecting whitespace-only new definitions, and allowing YAML formatting changes while preserving content and comments. After adding, return to refreshed Search Term results for the saved name. Require an existing valid file, preserve input on failures, allow a restricted transient local copy with normal cleanup, and stop on detected concurrent edits. The user accepts that those checks cannot guarantee protection against an editor writing at the exact same moment. See [ADR 0001](../../adr/0001-add-term-writes-glossary-file.md).

**Open design branches:** settle deletion behavior and editing scope; settle support for symbolic links and multiply linked files. The additions work below is detailed, but the expanded plan is not ready for implementation until these branches and shared understanding are settled.

1. Select a result in **Search Term** and open its action menu. **Add Term** opens a form with a **Term** text field, a multiline **Definition** field, and **Save Term**. Prefill Term with the current search query. Keep Add Term available when the glossary is empty or search has no matches.
2. Use the same Glossary File as Search Term. Require an existing valid `.yaml` file; support `terms: []`.
3. Trim surrounding whitespace from the submitted term name, then reject an empty result. Run duplicate validation on the trimmed name.
4. Reject empty or whitespace-only new definitions. For a definition with non-whitespace content, preserve its exact text, including whitespace and newlines. Existing file validation remains unchanged: previously valid whitespace-only definitions remain readable and are preserved when adding another term.
5. Reject duplicates with the existing `areTermsEquivalent` comparison, including case and canonical Unicode equivalence. Do not replace an existing term.
6. Append the new term in file order. Search continues to sort results independently.
7. Preserve existing values and comments through the YAML document API. Serialization may normalize whitespace or quoting; do not promise a byte-identical file layout.
8. While saving, show progress and guard against repeated submissions. On failure, retain both fields and show a safe error. On success, show **Term Added** and return to refreshed Search Term results for the saved name.
9. **Delete Term** acts on the selected term and removes its entry from the Glossary File; it does not delete the file. Deletion confirmation, stale-selection handling, and post-deletion selection are the next design branch.
10. **Edit Term** acts on the selected term. Whether it permits renaming as well as definition changes is the next design decision. Automatic watching, bulk import, and creating or repairing glossary files remain outside this version. Missing or invalid files produce safe errors with input preserved and file-selection recovery available.

### Privacy contract

The current README and AGENTS.md describe a read-only extension and prohibit persistence. The user has confirmed that explicit term actions may add, edit, or delete entries in the selected Glossary File, including a restricted transient sibling file for safe replacement. No persistent form drafts, caches, backups, glossary logging, telemetry, or network transmission.

Document the transient file honestly: a process crash may leave it behind. Normal runtime failure paths should clean up only the temporary file created by that save. The coding agent itself must not delete files; provide deletion commands if cleanup is needed during development. Do not change the privacy contract merely to facilitate unrelated persistence.

### Existing command and preference

Keep `glossaryFile` under the existing Search Term command in `package.json` and keep `Preferences.SearchTerm`. Pass that selected file path into the menu's forms/services. There is no standalone Add Term command and no preference-scope migration.

Update the preference description to cover searching and changing the glossary. Regenerate the ignored `raycast-env.d.ts` through Raycast build if needed; do not hand-edit or commit it.

## Task 1: Build and validate an updated glossary in memory

**Interfaces:**

```typescript
parseGlossarySource(source: string): readonly Term[];
appendGlossaryTerm(source: string, term: Term): string;
```

Keep `Term` from `src/utils/types.ts`. `parseGlossarySource` should compose `parseGlossaryDocument`, `rejectUnsupportedYaml`, and `parseGlossaryTerms`; `loadGlossary` retains its path and file checks and delegates parsing to it.

- [ ] Write failing tests in `append-glossary-term.test.ts`. Include this round-trip case:

```typescript
test("appends to an empty glossary without changing definition text", () => {
  const term = { term: "API", definition: "  first line\nsecond line\n" };
  const next = appendGlossaryTerm("# My glossary\nterms: []\n", term);
  expect(parseGlossarySource(next)).toEqual([term]);
  expect(next).toContain("# My glossary");
});
```

- [ ] Add cases for block and flow sequences, quoted strings, literal/folded definitions, comments, a document end marker, CRLF input, no final newline, punctuation resembling YAML, empty fields, trimming surrounding term whitespace, rejecting whitespace-only new definitions, and preserving meaningful definition whitespace. Verify existing whitespace-only definitions remain loadable and unchanged.
- [ ] Assert `API`/`api` and composed/decomposed Unicode duplicates fail with `duplicate-term`; accent-distinct terms remain allowed. Assert malformed source and unsupported constructs fail before transformation.
- [ ] Run `npm test -- src/glossary/append-glossary-term.test.ts`; confirm the new behavior is missing.
- [ ] Extract source validation without changing loader errors. Use a parsed YAML document rather than reconstructing existing entries from plain objects. The mutation uses the installed document API:

```typescript
const normalizedTerm = { term: term.term.trim(), definition: term.definition };
if (normalizedTerm.term.length === 0 || normalizedTerm.definition.trim().length === 0) {
  throw new GlossaryError("invalid-schema", "Term and definition must contain non-whitespace text.");
}
document.addIn(["terms"], document.createNode(normalizedTerm));
const nextSource = document.toString();
parseGlossarySource(nextSource);
```

- [ ] Validate source before mutation and candidate output afterward. Apply the new-input checks above in `appendGlossaryTerm` without tightening `parseGlossarySource` or `loadGlossary`. Candidate validation must reject invalid new fields and duplicates using existing rules, including a padded duplicate such as `API`. Compare decoded existing entries before and after to establish that serialization preserves definition values; cover trailing newlines and folded text explicitly.
- [ ] Export/reuse `maximumGlossaryBytes` from `glossary-file.ts`. Reject `Buffer.byteLength(nextSource, "utf8") > maximumGlossaryBytes` with `too-large`. Test exact-boundary and over-boundary output, including multibyte text.

## Task 2: Save an addition to the selected file

**Interface:**

```typescript
saveGlossaryTerm(path: string, term: Term): Promise<void>;
```

The service consumes `appendGlossaryTerm` and `readGlossarySource`; it has no Raycast or React dependency.

- [ ] Write filesystem tests using synthetic source and mocked filesystem operations for failures. Assert successful save produces a glossary accepted by `loadGlossary`, with original entries followed by the new term. Check actual source bytes remain unchanged on validation failure.
- [ ] Test missing files, directories, wrong extensions, read-only targets, oversized/invalid input, write/sync/rename failures, file replacement during save, and repeated calls. Assert no raw filesystem error or glossary content appears in public errors.
- [ ] Implement this ordered save protocol:
  1. Validate the extension and inspect the target. For the first version, reject symlinks and multiply linked files with a safe explanation; replacing them can change their link semantics. Search may continue reading such files.
  2. Serialize saves for the same path within the process, with a bounded in-memory queue that releases entries after completion.
  3. Read the latest source and capture target identity/metadata. Do this at submission time, not when the form opens.
  4. Build and validate the candidate with `appendGlossaryTerm`.
  5. Exclusively create a randomly named sibling temporary file with restrictive permissions. Write the complete candidate, flush, and close the handle. Preserve the target's ordinary permission bits without making the temporary file more broadly readable during construction.
  6. Recheck target identity/metadata and reread its bytes immediately before replacement. If the file changed, abort with `file-changed` and retain the user's form input.
  7. Rename the sibling over the target. Never fall back to truncating the original if replacement fails. Successful rename is the commit point; do not report failure afterward for a nonessential follow-up operation.
  8. On failure before replacement, close handles and clean up only this operation's temporary file. A cleanup failure must not obscure the original error.
- [ ] Add `unwritable`, `file-changed`, and `unsupported-write-target` to `GlossaryErrorCode`. Use static messages such as **The glossary changed while saving. Try again.** Do not include raw exceptions or term values.
- [ ] Test that failure before rename leaves the original intact and that concurrent same-process saves retain both additions. Verify successful saves leave no temporary file.
- [ ] Record the concurrency limit in README: reread checks reduce accidental overwrite but are not an atomic compare-and-swap against external editors or separate processes. Do not promise full concurrent-writer safety or crash durability on every filesystem. Recommend avoiding simultaneous external edits while saving.
- [ ] Update README and AGENTS.md with the narrow persistence contract alongside the writer. Preserve the agent prohibition on deleting files.
- [ ] Run focused writer and glossary suites. Delegate a local commit: `feat: save terms to the local glossary`.

## Task 3: Expose Add Term in the Search Term menu

**Consumes:** `saveGlossaryTerm(path, term)` and the existing shared `Term` type.

**Produces:** An Add Term action in the existing Search Term command and a nested form using its selected Glossary File.

The reusable form boundary is:

```typescript
type AddTermFormProps = Readonly<{
  glossaryFile: string;
  initialTerm?: string;
  onSaved: (term: Term) => Promise<void>;
}>;
```

The callback receives the trimmed saved name and the exact saved definition. The form and writer share the same input rules. Search Term supplies a callback that sets the query to the saved name, awaits `reload()`, and pops the form to show the current search state. The existing `reload()` records failures in search state instead of throwing; a failed refresh therefore returns to the Search Term error view without changing the successful save outcome.

- [ ] Keep the existing Search Term command registration and `getPreferenceValues<Preferences.SearchTerm>()`. Expose `glossaryFile: string` on the glossary controller returned by `useGlossary` and pass it to the nested form. Update preference description to **Select the local .yaml glossary to search and update**.
- [ ] Implement `src/components/add-term-form.tsx` using `Form.TextField`, `Form.TextArea`, and `Action.SubmitForm`. Use ids `term` and `definition`. Set `enableDrafts={false}` explicitly. The form is opened through the selected result's action menu; it is not a separately registered command.
- [ ] Add an Add Term action in `src/search-term.tsx`, using the shared form and passing the current query as `initialTerm`. Make it available from result actions, the empty glossary state, and the no-match state. Preserve existing copy and reload actions. A failed glossary load continues to expose file recovery actions.
- [ ] Validate fields on blur and submit, clearing field errors on edit. Trim the submitted name; reject empty names after trimming and whitespace-only definitions. Preserve meaningful definition text exactly. Match Task 1's rules. Show duplicate errors on Term, other safe errors in a failure toast, and provide **Open Extension Preferences** for file recovery.
- [ ] Use a synchronous ref guard plus loading state around the awaited save; a loading indicator alone does not prevent double submission. Retain entered text on failure. After success, show **Term Added** and invoke the Search Term callback described above. Separate save failure handling from post-save navigation/refresh handling: once the writer resolves, a later failure must not be reported as a failed save or enable a duplicate retry. Do not expose raw errors through diagnostic toasts.

- [ ] Run `npm test`, `npm run lint`, `npm run check:format`, and `npm run build`. Existing tests include cleanup that deletes temporary directories; if the agent's no-deletion policy blocks running them, report checks as blocked and provide those exact commands for the user instead of bypassing the restriction.

## Expanded scope: Edit Term and Delete Term

Both Edit Term and Delete Term are confirmed menu actions. Their detailed implementation tasks will follow the next design round. Carry these concrete scenarios into that round:

- Removing the selected term must operate on its identity, not its index in the filtered or sorted results.
- If the selected term was edited or removed externally since it was displayed, decide whether to reject deletion as stale; the recommendation is to reject and refresh.
- Decide whether Delete Term asks for confirmation and what happens to the current query/selection afterward. The recommendation is confirmation followed by a refresh with the existing query preserved.
- Deleting the last term must leave a valid empty Glossary File (`terms: []`), not remove the file.
- Reuse the validated replacement mechanism and preserve all surviving term values. Decide how comments belonging to the removed entry should be treated.
- Decide whether Edit Term permits renaming or changes only the definition. The recommendation is both, with duplicate checks excluding the original selected term.
- Editing starts from the selected term's name and definition, not the search query. Define stale-selection handling and preservation of comments before choosing a shared mutation interface.

These are explicit open design questions, not settled delete or edit behavior. Preserve the completed additions design while extending the plan to cover the agreed menu. Refactor the addition-specific writer into a common mutation service when detailing edit/delete, so all three actions use the same validation, conflict detection, and replacement protocol.

## Acceptance matrix

| Scenario                                           | Expected result                                                                                      |
| -------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| Existing Search Term setup                         | Existing command-level file preference supplies all actions; no new command or preference migration. |
| Add to empty and populated files                   | Exactly one new term is saved; it appears after reopening Search Term or reloading.                  |
| Open Add Term inside Search Term                   | Shared form opens with the search query prefilled, including from the no-match state.                |
| Save from Search Term                              | Returns to refreshed results with the saved term name as the query.                                  |
| Search refresh fails after a successful save       | Save remains successful; returning search shows its load error and recovery actions.                 |
| Missing or invalid Glossary File                   | No creation or repair; entered text remains available and file-selection recovery is offered.        |
| Multiline text, punctuation, and trailing newline  | Definition copies back exactly; existing definitions and comments survive.                           |
| Empty or whitespace-only name/definition           | Clear field error; no file change.                                                                   |
| Padded name such as `API`                          | Saves as `API`, or reports a duplicate if `API` already exists.                                      |
| Existing whitespace-only definition                | Still loads and remains unchanged when a different term is added.                                    |
| Case or Unicode-equivalent duplicate               | Duplicate error; original file and input remain intact.                                              |
| Invalid YAML, wrong extension, or oversized output | Safe error; no replacement.                                                                          |
| Read-only or unsupported target                    | Safe recovery message; no damage to the original.                                                    |
| Detected external edit or injected write failure   | Save aborts; original/current external contents remain; input retained.                              |
| Rapid repeated submit                              | One save for that submission; form resets only after success.                                        |
| Cancel and reopen                                  | No glossary change and no persisted form draft.                                                      |
| Existing search, reload, and clipboard actions     | Existing behavior remains unchanged.                                                                 |
