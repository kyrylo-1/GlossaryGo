# Term Actions Design and Implementation Plan

> **For agentic workers:** Use superpowers:executing-plans to implement this plan task by task. Steps use checkboxes for tracking. Delegate each local commit to a separate `gpt-5.6-luna` agent with low reasoning, as required by this repository.

**Goal:** Add **Add Term**, **Edit Term**, and **Delete Term** to the existing **Search Term** window's action menu.

**Architecture:** Keep Search Term as the single Raycast command. Its selected-result action menu opens Add Term or Edit Term forms and offers Delete Term for that selection. Pure YAML transformations and a shared file-writing service reuse the existing validation pipeline. The current command-level Glossary File preference supplies the target path.

**Tech Stack:** TypeScript, React, Raycast API, the installed `yaml` package, Node filesystem APIs, and Vitest. No new runtime dependency is planned.

**Spec:** The behavior and decisions below form the design for this plan. This is a planning artifact, not an instruction to begin implementation.

## Behavior and decisions

**Confirmed scope:** **Add Term**, **Edit Term**, and **Delete Term** are actions in the existing Search Term window's menu. Keep one command and its current file preference.

**Retained decisions:** direct saving with search-query prefill, duplicate rejection, trimming new term names, rejecting whitespace-only new definitions, and allowing YAML formatting changes while preserving content and comments. After adding, return to refreshed Search Term results for the saved name. Require an existing valid file, preserve input on failures, allow a restricted transient local copy with normal cleanup, and stop on detected concurrent edits. The user accepts that those checks cannot guarantee protection against an editor writing at the exact same moment. See [ADR 0001](../../adr/0001-add-term-writes-glossary-file.md).

**Design status:** all interview choices are confirmed. Edit both the name and definition. Confirm deletion, preserve the search query afterward, and remove comments attached to the deleted entry while retaining glossary and surviving-entry comments. Require ordinary files; reject symbolic links and multiply linked files. This completed plan does not start implementation.

1. Select a result in **Search Term** and open its action menu. **Add Term** opens a form with a **Term** text field, a multiline **Definition** field, and **Save Term**. Prefill Term with the current search query. Keep Add Term available when the glossary is empty or search has no matches.
2. Use the same Glossary File as Search Term. Require an existing valid `.yaml` file; support `terms: []`.
3. Trim surrounding whitespace from the submitted term name, then reject an empty result. Run duplicate validation on the trimmed name.
4. Reject empty or whitespace-only new definitions. For a definition with non-whitespace content, preserve its exact text, including whitespace and newlines. Existing file validation remains unchanged: previously valid whitespace-only definitions remain readable and are preserved when adding another term.
5. Reject duplicates with the existing `areTermsEquivalent` comparison, including case and canonical Unicode equivalence. Adding cannot replace an existing term; editing excludes the original selected term from duplicate comparisons.
6. Append the new term in file order. Search continues to sort results independently.
7. Preserve surviving values and comments through the YAML document API. Editing retains the selected entry's comments; deleting removes comments attached to that entry. Serialization may normalize whitespace or quoting; do not promise a byte-identical file layout.
8. While saving, show progress and guard against repeated submissions. On failure, retain both fields and show a safe error. On success, show **Term Added** and return to refreshed Search Term results for the saved name.
9. **Delete Term** asks for confirmation identifying the selected term, then removes that entry and its attached comments. Preserve the search query and reload; Raycast can select the first remaining matching result. Deleting the last entry leaves a valid empty file. Canceling confirmation does not write anything.
10. **Edit Term** opens a form prefilled with the selected name and definition and permits changes to both. Apply the same input rules as Add Term. Preserve its position in the file, show **Term Updated**, and return to refreshed results for the saved name. Automatic watching, bulk import, and creating or repairing glossary files remain outside this version. Missing or invalid files produce safe errors with input preserved and file-selection recovery available.

### Privacy contract

The current README and AGENTS.md describe a read-only extension and prohibit persistence. The user has confirmed that explicit term actions may add, edit, or delete entries in the selected Glossary File, including a restricted transient sibling file for safe replacement. No persistent form drafts, caches, backups, glossary logging, telemetry, or network transmission.

Document the transient file honestly: a process crash may leave it behind. Normal runtime failure paths should clean up only the temporary file created by that save. The coding agent itself must not delete files; provide deletion commands if cleanup is needed during development. Do not change the privacy contract merely to facilitate unrelated persistence.

### Existing command and preference

Keep `glossaryFile` under the existing Search Term command in `package.json` and keep `Preferences.SearchTerm`. Pass that selected file path into the menu's forms/services. There is no standalone Add Term command and no preference-scope migration.

Update the preference description to cover searching and changing the glossary. Regenerate the ignored `raycast-env.d.ts` through Raycast build if needed; do not hand-edit or commit it.

### Selected terms and comments

Capture the selected term's name and definition when opening Edit Term or requesting Delete Term. Before writing, reread the latest file, locate the original term by name equivalence, and require its exact name and definition to still match that snapshot. A missing or changed selection produces `stale-term`; preserve unsaved form input and offer a search reload. Unrelated file edits made before this latest read are retained. File changes detected between read and replacement produce `file-changed` instead.

Comment ownership follows the parsed YAML document: comments on the entry mapping and its descendant nodes belong to the term; document, root, and sequence comments belong to the glossary. The installed parser may attach a comment above the first entry to the sequence, so that comment survives deletion of the first entry. Test this distinction rather than assuming that physical proximity establishes ownership.

## Global constraints

- Use only npm. Honor `package.json`'s actual Node requirement, `>=22.22.2`, which is stricter than the older prose guidance.
- Preserve `.yaml` only, strict UTF-8, a maximum of 5 MiB, exactly one document, existing schema rules, and unsupported-YAML rejection.
- Enforce the 5 MiB limit on serialized UTF-8 bytes, not JavaScript string length.
- Keep glossary values local; use synthetic values in all examples and tests.
- Preserve unrelated working-tree changes. Never revert commits or delete files as an agent.
- Read `vercel-react-best-practices` before implementing TSX changes.
- Make each numbered task a focused, independently validated local commit through the required Luna agent. Do not push.

## Task 1: Transform and validate additions, edits, and deletions in memory

**Interfaces:**

```typescript
type GlossaryChange =
  | Readonly<{ type: "add"; term: Term }>
  | Readonly<{ type: "edit"; original: Term; term: Term }>
  | Readonly<{ type: "delete"; original: Term }>;

parseGlossarySource(source: string): readonly Term[];
applyGlossaryChange(source: string, change: GlossaryChange): string;
```

Keep `Term` from `src/utils/types.ts` and export `GlossaryChange` from `apply-glossary-change.ts`. `parseGlossarySource` should compose `parseGlossaryDocument`, `rejectUnsupportedYaml`, and `parseGlossaryTerms`; `loadGlossary` retains its path and file checks and delegates parsing to it. Add `stale-term` to `GlossaryErrorCode` with static text: **The selected term changed or was removed. Reload the glossary and try again.**

- [ ] Write failing tests in `apply-glossary-change.test.ts`. Include this round-trip case:

```typescript
test("appends to an empty glossary without changing definition text", () => {
  const term = { term: "API", definition: "  first line\nsecond line\n" };
  const next = applyGlossaryChange("# My glossary\nterms: []\n", { type: "add", term });
  expect(parseGlossarySource(next)).toEqual([term]);
  expect(next).toContain("# My glossary");
});
```

- [ ] Add cases for block and flow sequences, quoted strings, literal/folded definitions, comments, a document end marker, CRLF input, no final newline, punctuation resembling YAML, empty fields, trimming surrounding term whitespace, rejecting whitespace-only new definitions, and preserving meaningful definition whitespace. Verify existing whitespace-only definitions remain loadable and unchanged.
- [ ] Assert `API`/`api` and composed/decomposed Unicode duplicates fail with `duplicate-term`; accent-distinct terms remain allowed. Assert malformed source and unsupported constructs fail before transformation.
- [ ] Run `npm test -- src/glossary/apply-glossary-change.test.ts`; confirm the new behavior is missing.
- [ ] Add focused edit/delete tests, including these cases:

```typescript
test("renames the selected term without treating it as a duplicate of itself", () => {
  const original = { term: "API", definition: "Old definition" };
  const source = "terms:\n  - term: API\n    definition: Old definition\n";
  const term = { term: "api", definition: "New definition\n" };
  expect(parseGlossarySource(applyGlossaryChange(source, { type: "edit", original, term }))).toEqual([term]);
});

test("deleting the last term retains an empty glossary and glossary comments", () => {
  const original = { term: "API", definition: "Example" };
  const source = "# Glossary notes\nterms:\n  - term: API\n    definition: Example\n";
  const next = applyGlossaryChange(source, { type: "delete", original });
  expect(parseGlossarySource(next)).toEqual([]);
  expect(next).toContain("terms: []");
  expect(next).toContain("# Glossary notes");
});
```

- [ ] Test rename collisions with another entry, selecting a term whose sorted-result position differs from file position, stale name/definition snapshots, already-removed terms, preserving edited scalar comments, deleting entry/field comments, and preserving root/sequence/surviving comments. Apply stale-selection checks to edits and deletes before mutation.
- [ ] Extract source validation without changing loader errors. Use a parsed YAML document rather than reconstructing existing entries from plain objects. For add/edit, normalize and validate the submitted term:

```typescript
const normalizedTerm = { term: change.term.term.trim(), definition: change.term.definition };
if (normalizedTerm.term.length === 0 || normalizedTerm.definition.trim().length === 0) {
  throw new GlossaryError("invalid-schema", "Term and definition must contain non-whitespace text.");
}
```

- [ ] Obtain the validated terms sequence using `document.get("terms", true)` and narrow with `isSeq`. For edit/delete, find the original entry in the parsed terms using `areTermsEquivalent`, then check exact original name and definition. Reject a missing or changed original with `stale-term`. The matched index is a file-sequence index, never a search-result index.
- [ ] Apply the selected mutation using the installed YAML APIs:

```typescript
// Add after validating change.term:
document.addIn(["terms"], document.createNode(normalizedTerm));

// Edit after narrowing the matched sequence item with isMap:
const termScalar = entry.get("term", true);
const definitionScalar = entry.get("definition", true);
if (!isScalar(termScalar) || !isScalar(definitionScalar)) {
  throw new GlossaryError("invalid-schema", "The selected term must have string fields.");
}
termScalar.value = normalizedTerm.term;
definitionScalar.value = normalizedTerm.definition;

// Delete from the validated sequence:
sequence.delete(index);

// Serialize and validate after the chosen branch:
const nextSource = document.toString();
parseGlossarySource(nextSource);
```

Updating scalar values retains their node comments and works with the installed parsed-node TypeScript types. Do not replace the entire mapping for edits. Deleting the mapping removes its attached comments and descendants; retain parent comments. An empty sequence with comments may serialize across several lines rather than as the literal text `terms: []`; assert the decoded empty glossary and retained comments in that case. A no-change edit may return the original source without rewriting it.

- [ ] Validate source before mutation and candidate output afterward. Apply new-input checks only to add/edit without tightening `parseGlossarySource` or `loadGlossary`. Candidate validation catches duplicates after the original entry has been updated, naturally excluding that original from rename comparisons. Verify preserved entries retain exact values, especially multiline definitions and trailing newlines.
- [ ] Export/reuse `maximumGlossaryBytes` from `glossary-file.ts`. Reject `Buffer.byteLength(nextSource, "utf8") > maximumGlossaryBytes` with `too-large`. Test exact-boundary and over-boundary output, including multibyte text.
- [ ] Run focused and existing glossary suites, lint, format checks, and build. Delegate a local commit: `feat: validate glossary term changes`.

## Task 2: Save all term changes through one file service

**Interface:**

```typescript
saveGlossaryChange(path: string, change: GlossaryChange): Promise<void>;
```

The service consumes `GlossaryChange`, `applyGlossaryChange`, and bounded file-reading operations; it has no Raycast or React dependency. The protocol is identical for add, edit, and delete. Return only after the replacement commits; deleting a term must never unlink the selected Glossary File.

- [ ] Write filesystem tests using synthetic source and mocked filesystem operations for failures. Assert successful save produces a glossary accepted by `loadGlossary`, with original entries followed by the new term. Check actual source bytes remain unchanged on validation failure.
- [ ] Test missing files, directories, wrong extensions, read-only targets, oversized/invalid input, write/sync/rename failures, file replacement during save, and repeated calls. Assert no raw filesystem error or glossary content appears in public errors.
- [ ] Implement this ordered save protocol:
  1. Validate the extension and inspect the target. For the first version, reject symlinks and multiply linked files with a safe explanation; replacing them can change their link semantics. Search may continue reading such files.
  2. Serialize saves for the same path within the process, with a bounded in-memory queue that releases entries after completion.
  3. Read the latest source and capture target identity/metadata and original bytes. Do this at submission time, not when the form opens. Extend the bounded reader in `glossary-file.ts` to expose a snapshot if needed; retain strict UTF-8 decoding and compare original bytes, including any byte-order mark, when detecting changes.
  4. Build and validate the candidate with `applyGlossaryChange(source, change)`. Stale selected-term snapshots abort before any temporary write. Skip replacement when the candidate is identical to the source.
  5. Exclusively create a randomly named sibling temporary file with restrictive permissions. Write the complete candidate, flush, and close the handle. Preserve the target's ordinary permission bits without making the temporary file more broadly readable during construction.
  6. Recheck target identity/metadata and reread its bytes immediately before replacement. If the file changed, abort with `file-changed` and retain the user's form input.
  7. Rename the sibling over the target. Never fall back to truncating the original if replacement fails. Successful rename is the commit point; do not report failure afterward for a nonessential follow-up operation.
  8. On failure before replacement, close handles and clean up only this operation's temporary file. A cleanup failure must not obscure the original error.
- [ ] Add `unwritable`, `file-changed`, and `unsupported-write-target` to `GlossaryErrorCode`. Use static messages such as **The glossary changed while saving. Try again.** Do not include raw exceptions or term values.
- [ ] Test that failure before rename leaves the original intact, same-process additions retain both additions, and stale queued edit/delete requests are rejected. Test safe edit replacement, successful deletion without unlinking the selected file, and repeated deletion yielding `stale-term`. Verify successful saves leave no temporary file.
- [ ] Record the concurrency limit in README: reread checks reduce accidental overwrite but are not an atomic compare-and-swap against external editors or separate processes. Do not promise full concurrent-writer safety or crash durability on every filesystem. Recommend avoiding simultaneous external edits while saving.
- [ ] Update README and AGENTS.md with the narrow persistence contract alongside the writer. Preserve the agent prohibition on deleting files.
- [ ] Run focused writer and glossary suites, lint, format checks, and build. Delegate a local commit: `feat: safely persist glossary term changes`.

## Task 3: Expose Add Term in the Search Term menu

**Consumes:** `saveGlossaryChange(path, change)`, `GlossaryChange`, and the existing shared `Term` type.

**Produces:** An Add Term action in the existing Search Term command and a nested form using its selected Glossary File.

The reusable form boundary is:

```typescript
type TermFormProps = Readonly<{
  glossaryFile: string;
  onSaved: (term: Term) => Promise<void>;
}> &
  (Readonly<{ mode: "add"; initialTerm?: string }> | Readonly<{ mode: "edit"; original: Term }>);
```

The callback receives the trimmed saved name and the exact saved definition. The form and writer share the same input rules. Search Term supplies a callback that sets the query to the saved name, awaits `reload()`, and pops the form to show the current search state. The existing `reload()` records failures in search state instead of throwing; a failed refresh therefore returns to the Search Term error view without changing the successful save outcome.
